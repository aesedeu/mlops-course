# Celery на пальцах

Игрушечный пример: как задача создаётся, попадает в очередь и исполняется воркером.
Это та же механика, на которой работает `CeleryExecutor` в Airflow.

```
client ──.delay()──▶ Redis /0 (очередь) ──▶ worker ──результат──▶ Redis /1 ──.get()──▶ client
```

## Кто есть кто

| Роль | Файл | Что делает | В Airflow |
|---|---|---|---|
| **Приложение** | `tasks.py` | `Celery(...)`: адрес брокера и backend + список задач (`@app.task`) | `airflow.providers.celery...celery_executor.app` |
| **Брокер** | Redis `/0` | очередь сообщений «выполни задачу X с аргументами Y» | `redis` |
| **Воркер** | `celery -A tasks worker` | слушает очередь, берёт сообщение, выполняет функцию | `airflow-worker` |
| **Клиент** | `client.py` | кладёт задачи в очередь, ждёт результат | `airflow-scheduler` |
| **Result backend** | Redis `/1` | статус и результат задачи | Postgres (`db+postgresql://...`) |

Главное: **клиент задачу не выполняет**. `.delay()` только кладёт в Redis сообщение
с именем функции и аргументами. Код функции выполняет воркер, поэтому `tasks.py`
должен быть и у клиента, и у воркера.

## Запуск

```bash
docker compose up -d --build        # redis + 1 воркер
docker compose logs -f worker       # в соседнем терминале смотреть, как воркер берёт задачи
docker compose run --rm client      # отправить задачи
```

Ожидаемый вывод клиента:
```
отправили add(2, 3), id=348e..., state=PENDING
результат: 5, state=SUCCESS

отправили 6 x slow_square, состояния: ['PENDING', ...]
   {'x': 0, 'square': 0, 'worker': 'd1a4ad8c2a27'}
   ...
6 задач по 3 c выполнены за 9.0 c

fail(): state=FAILURE, ошибка=ValueError('упали нарочно')
```

Что видно:
1. **`PENDING` → `SUCCESS`**: сразу после `.delay()` задача лежит в очереди, а `.get()` ждёт, пока воркер запишет результат.
2. **Параллельность**: 6 задач по 3 с выполнились за 9 с, а не за 18, потому что у воркера `--concurrency=2` (два процесса).
3. **Ошибка изолирована**: исключение в задаче не роняет воркер, а возвращается клиенту со статусом `FAILURE`.

## Масштабируем воркеры

```bash
docker compose up -d --scale worker=3
docker compose run --rm client
```
```
   {'x': 0, 'square': 0, 'worker': '437fdd8dfa08'}
   {'x': 1, 'square': 1, 'worker': 'd1a4ad8c2a27'}
   {'x': 2, 'square': 4, 'worker': '03458af85098'}
   ...
6 задач по 3 c выполнены за 3.0 c
```
Три воркера по 2 процесса — все 6 задач идут одновременно, и они разошлись по
разным контейнерам (разный `worker`). Клиент ничего не менял: он просто кладёт
задачи в очередь, а кто и сколько их разбирает, решает количество воркеров. Так же
в Airflow масштабируют `airflow-worker`.

## Убрать

```bash
docker compose down
```
